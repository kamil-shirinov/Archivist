# Decisions — one line each: decision — why
D1 Indie track, "Build for Your World" — a problem seen first-hand during a bank internship.
D2 One document family: running-balance ledger cards plus the payment memos that reference them — they carry built-in checksums (balances, words vs figures, memo vs ledger).
D3 Data: synthetic with exact ground truth plus public-domain scans — rights-clean, nothing private.
D4 Checks independent of the extractor: arithmetic in plain code; blind re-reads never see the claimed value — correlated checks add no information.
D5 One interface per capability (VisionLLM, Segmenter), wrapped as Cache(Budget(Backend)), roles mapped in models.toml — swaps are config changes, the cap can't be bypassed, the cache doubles as replay.
D6 Plan A runs entirely on the Meta Model API (Muse Spark + SAM 3.1) — partner credits only ever add a second arm.
D7 Models chosen per role on dev; each configuration pre-registered and run once on the frozen test set — choosing on test inflates results.
D8 Hard spend cap $120 in code plus $30 untouched buffer — the Billing spend limit only notifies.
D9 Pre-printed line numbers on ledger cards — deterministic row alignment in evaluation.
D10 Source errors are flagged, never auto-corrected; ground truth is the printed value — Archivist reports what the document says.
D11 Python 3.12 with a uv lockfile — reproducible runs.
D12 The UI is a static app over a run bundle exported by the pipeline; the browser never calls a model — it can't break live, exposes no key, spends nothing, and can be built against a fixture.
D13 No public live mode — an upload box invites documents outside our one family; live runs are shown in the video and documented for local use.
D14 Only synthetic or public-domain pages are ever sent to a model — free-credit traffic may be used by Meta for product improvement.
D15 Rubric weights (kickoff): Impact 30, Meta tooling 25, Demo 25, Technical depth 20 — optimise in that order; rigour exists to make the impact claims credible.
D16 Datasets keep images and ground truth in separate folders, with a hashed manifest — the pipeline can't see answers by accident, and any change to the data is detectable.
D17 Scans are stored as JPEG at their level's quality — that is what a real scan file is, at about a quarter of the size. Dev images are rebuilt from the seed rather than committed; only the frozen test set is committed in full.
D18 Every paid model call is logged in results/spend_ledger.jsonl, which is committed — cost per page is part of the evidence, and the cap is enforced from the same file.
D19 Muse Spark runs as muse-spark-1.3-contributor: the same 1.3 model in Contributor mode, at Contributor prices. Allowed because only synthetic or public-domain pages are ever sent (D14); real deployments would use Standard mode or open weights.
D20 Scoring rules are written and tested before any model output is scored — the definitions can't drift toward flattering results.
D21 Document types are plug-ins (fields, prompt, schema, parser; checks come next). One is built: ledger cards with their payment memos. Each page is classified first; anything unrecognised is reported as unsupported, never forced into a template.
D22 Amount in words is compared on its letters only — spelling variants of the same words aren't errors. Fixed on dev after the baseline exposed it, before the test set exists.
D23 Citations default to S0+ink: S0's boxes corrected from the page image with a per-page skew-aware fit (y = α·y + β + γ·x), which raised citation accuracy from 63.4% to 92.6% with fewer citations in another field's box (9.9% to 4.0%) — built and tuned on dev, frozen, then validated once on a separate split (val, seed 2002) it had never seen, under a rule fixed in advance; the frozen test set gives the final number.
D24 Deterministic checks use only rules a bank clerk would recognise — balances, dates, cheque sequences, words against figures, memos against the ledger — never constants from our generator, so they carry over to real archives.
D25 Arithmetic verifies the money; an independent blind re-read verifies everything else. Archivist never changes a value: it proposes a correction with its evidence, and a person decides.
D26 Every value is read twice: once in context and once in isolation. Validation showed in-context reading can make a mistake add up — a misread debit carried through every later balance — so the arithmetic alone passed it. An isolated re-read sees one cell at a time and can't make numbers agree. Dev and val are now both development data; the test set will be frozen before the final policy runs on it once.
D27 Muse Spark Open runs on Baseten (meta-models/muse-spark-open-1026) as a second Meta model, with its own spend cap. Which model does which job is decided by measurement (D7).
D28 Muse Spark Open sometimes ends a long JSON answer one bracket short while reporting a normal stop. The backend closes the missing brackets only when the answer finished normally and then parses; values are never altered, and every repair is logged.
D29 A second look before raising an alarm (policy v3) was tested on dev and val. It cut review by about a third but missed more errors, and its proposals were mostly wrong, so it was not adopted. The headline — arm A under policy v2 — was chosen by a rule fixed before the comparison ran, on dev and val pooled; arms B and C are reported alongside.
D30 The test set was generated once and committed with the pre-registration before any part of the pipeline ran on it; each configuration runs on it exactly once (PREREGISTRATION.md).
D31 New table types can be template files instead of code: Muse Spark drafts a template (layout, columns, identities) from 2-3 development pages, an arithmetic test reads the pages twice and evaluates every identity on cells both reads agree on, and only a person approves it, with the evidence file's sha256 recorded; a run uses only the types its config enables, so approving one never changes a committed run — the model proposes, arithmetic tests, a person decides, as for values (D25).
D32 Each document type names its own box strategy: ledger cards and memos keep S0+ink (D23); templates use S0+ocr, each value's box taken from the archive PDF's own OCR text layer where exactly one matching figure lies near the model's box, else the model's box, unanchored. Chosen by the rule written before running (the higher share of sampled cells whose two reads agree; a tie keeps S0) on development pages: 52.2% against S0's 34.7%, 85% on anchored cells; S0+ink, tuned on synthetic cards, moved some Treasury boxes by hundreds of pixels (results/templates/citations_dev.md, citations_dev_v2.md). S0+ocr reads PDFs, so it stays out of the pipeline, which reads page images only.
D33 Template re-reads run at reasoning "minimal" (config/templates.toml); the committed configs keep "low" — at "low" a one-cell re-read spent a median 758 output tokens reasoning and about one answer in six used the whole 2,048-token allowance and came back empty; at "minimal" no cell ran out (results/templates/citations_dev.md, citations_dev_v2.md).
D34 Collections of Internal Revenue is set aside until templates can describe multi-panel tables (P21d): its title covers two different tables, each printed as two panels on one page, and a page is classified as one type; the next eligible family under the same rule took its place, before any held-out page was touched (results/real/family_choice.md).
D35 Templates now take their boxes by S0+grid: the OCR layer's box where the figure is found there, else the cell of the table's grid found in the page by plain code, else the model's, each cell recording its source. Chosen by the same pre-written rule on the same development pages: 61.0% of sampled cells agree against S0+ocr's 45.1%, and grid boxes agree 67% where the model's agree 17% (results/templates/citations_dev_v3.md). It supersedes D32's S0+ocr for templates; the ledger family keeps S0+ink.
D36 A template's rows may be read in sections under printed headings, and an identity may hold at each position within sections (a total section equal to the sum of others, row by row), so a table whose sections change length from issue to issue is described once — the forward exchange table's purchase and sale totals could not be written over rows numbered from the top.
D37 S0+grid bounds each table's body by its horizontal rules: a band on a rule is the rule's leftover stroke, and the stretch between rules whose band count is closest to the read's printed rows is the body, so a heading, a column-number line or the next table cannot add bands. Kept by the pre-written rule on 20 development pages: 56.4% of sampled cells agree against 54.9%; one page got worse (1982-06 p091, 19 to 17 of 40, where bounding dropped bands that held fixed rows) and two better (1984-06 p055, 8 to 21; 1983-06 p092, 34 to 35) (results/templates/citations_dev_v5.md). A page with no fixed row may map rows by order only when its bands equal its rows and 15 of 20 cells re-read blind agree; on its first trial (1983-06 p088) the guard refused it, 3 of 20. Splitting merged lines was not tried: 1983-06 p097 falls short because rows of asterisks print too little ink to form a band, not because lines merge.
